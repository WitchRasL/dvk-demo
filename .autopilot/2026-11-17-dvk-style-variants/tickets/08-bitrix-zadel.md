# 08 — Задел под Битрикс: записка о подключении каталога

**Требования:** A01
**Зависит от:** 02, 03
**Зона:** `docs/bitrix-integration.md`
**Волна:** 4
**Ревью:** нет
**Модель:** обычная

## Что должно заработать

Заказчик и разработчик полного сайта открывают один документ и понимают, как товары из Битрикс текущего dvk-style.ru будут попадать на новый сайт: какие есть пути, какой рекомендуется и почему, как поля инфоблока ложатся на нашу схему данных, и что для этого нужно от заказчика. Кода проекта этот таск не меняет.

## Из брифа, дословно

> «сайт должен быть интегрирован с Битрикс, то есть все продукты с текущего сайта клиента dvk-style.ru должны аналогично с Битрикс подтягиваться в наш обновленный сайт»
> «Полностью пока сайт не создавай, нужны главные страницы, чтобы можно было выбрать и показать заказчику и далее уже будем полноценно обновлять сайт со всеми продуктами с текущего сайта»
> «Если не уверен в факте о компании, проверь его на сайте, а не додумывай.»

## Разделы спецификации

История 81; «Вне рамок» → «Подключение каталога к Битрикс (G02)»; `interfaces.md` → «Схема данных», итоги T02 и T03.

## Что прочитать

`src/core/catalog/data.js` (единственное место, где читаются JSON), `src/data/*.json` (схема), `scripts/collect/*` и `docs/content-sources.md` (как данные собраны сейчас). С живого сайта — только публичные адреса, с паузой 0,5–1 с и с соблюдением `robots.txt`: главная, одна страница раздела, одна страница товара, `robots.txt`, `sitemap.xml`. Закрытые адреса (`/bitrix/admin/` и т. п.) не открывать, формы не отправлять, ничего не подбирать.

## Критерии приёмки

- [ ] `docs/bitrix-integration.md` на русском, 1–2 экрана, без воды
- [ ] «Что видно снаружи»: по каким признакам сайт работает на 1С-Битрикс (пути `/bitrix/`, `/upload/iblock/`, заголовки, мета) — только то, что реально проверено, с адресами; чего проверить нельзя — `[уточнить]`; найдена ли публичная выгрузка (YML в `/bitrix/catalog_export/`, `sitemap.xml`) — да/нет по факту
- [ ] Три пути подключения, у каждого — как работает, что нужно от заказчика, плюсы, минусы, когда выбирать: (1) новый дизайн как шаблон сайта в самом Битрикс (сайт остаётся на Битрикс, каталог родной); (2) отдельный фронтенд + данные из Битрикс при сборке (выгрузка YML/CommerceML или REST → те же `src/data/*.json`, обновление по расписанию); (3) отдельный фронтенд + запросы к Битрикс на лету (свой JSON-адрес/REST, CORS, кэш)
- [ ] Рекомендация одним абзацем — какой путь брать по умолчанию и от какого ответа заказчика это зависит (редакция Битрикс, есть ли модуль «Торговый каталог», кто администрирует)
- [ ] Таблица «поле Битрикс → поле нашей схемы» для товара, раздела и фото (`NAME`, `CODE`, `IBLOCK_SECTION_ID`, `DETAIL_PICTURE`, `PROPERTY_*`, цена и т. д.) — по реальным полям `products.json`/`categories.json`; где соответствие неизвестно без доступа — `[уточнить]`
- [ ] «Что уже готово в прототипе»: единая точка чтения данных (`src/core/catalog/data.js`), схема, алиасы старых названий, сборщик `scripts/collect` — что из этого переиспользуется в каждом пути
- [ ] «Что нужно от заказчика» — списком; доступы и ключи называются только по именам (например `BITRIX_WEBHOOK_URL`), значения не запрашиваются и не записываются
- [ ] Ни одного выдуманного факта о сайте и компании; `npm run check` остаётся зелёным (код не тронут)
